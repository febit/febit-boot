# 设计模板

> 产品设计只阐述三件事： **它是什么**、 **它怎么变**、 **为什么这样**。

## 阐述什么

| 问题           | 阐述                                      |
|----------------|-------------------------------------------|
| **它是什么**   | 领域概念、实体构成、聚合归属、各自的规则  |
| **它怎么变**   | 状态流转、生命周期、交互                  |
| **为什么这样** | 关键取舍：选 A **而非** B，因为 C，代价 D |

「为什么」长在被决策的结论旁，规则长在它所约束的对象下——读者看到结论的同一处，就该看到它为什么成立。

## 性质要求（作用于每一条陈述）

- 会因一次提交而失效的，不属于设计
- 不写「怎么做到的」——那是实现

> 「永远成立」是 **每条陈述的性质**，不是一个条目或一节。

## 禁令

- **实现**：类名、方法、表结构、SQL、配置值 → 代码是唯一真相
- **进度与状态头**（已完成 / 部分实现 / 待建）→ 由代码回答
- **顶层清单节**：把边界声明、验证清单、实现名录或规则单独列成节——抽离所属对象即失根
- **决策推敲的来回过程**写在结论旁，本文只留定案结论（不另立 evolution 文档）

> **设计固有代价**（选 AP 而非 CP，代价是短暂不一致）留本文； **待修缺陷**不进设计文档。

## 参考结构

> 示例，不是清单；节名随内容自然生成。

**概念型**（领域概念 / 状态）：

```markdown
# [子域]设计

## 概念区分
## 领域定义 / 聚合根  —— 它是什么
   ### [实体] —— 标识 / 属性 / 关系 / 规则，条目名随内容定
## 状态流转        —— 它怎么变
## 关键规则表      —— 谁能做什么
## 并发与一致性    （仅当存在竞态时）
```

**机制型**（守护纠错 / 重试 / 清理）：

```markdown
# [机制]设计

## 设计原则
## 异常发现手段    —— 它怎么感知
## 纠正动作 / 检测  —— 它怎么做
## 重试与升级
## 超时处理
```

机制节名天然领域特定，照实命名。

> 合格判据：删掉全部「是什么」后，若「为什么」所剩无几 → 只是目录清单。
