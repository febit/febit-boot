# 注释规范

> Java 代码注释 **红线**；只在此定义，不在 [coding-java](coding-java.md) 重复。

正向范式与语料（怎么写好 Javadoc）见
[clean-code / comments](../skills/clean-code/references/comments.md)——
本文件只定义禁止什么、何时必须写。

## 一条原则

命名即文档，注释是例外。能用命名 / 结构 / 类型表达的，一律不写。
代码能追踪到的（数据来源、职责分工、流程步骤、实现方式、调用前提）一律不写。
「为什么」只有在该信息缺失会导致 **错误或安全漏洞**时才值得写。

## 存量清理

设计动机 / 实现说明 / 数据来源 / 使用前提 / 职责边界 / 组件用途 / 步骤流程类注释默认删除；
仅保留删后会导致错误或安全隐患者。改代码时同步删改失效注释。

既有 `TODO` / `FIXME` 不清理，只在确实已解决时移除。

## 仅两类值得写（其余默认删）

**1. 安全 / 正确性关键约束**——删了会出错或引发安全漏洞（竞态、越权、数据损坏、时序破坏）。

```java
// 最后 Owner 保护：不得移除
// 防 lost-wakeup：先注册再查库
```

**2. 协议 / 契约 + workaround**——API 消费者必须知道；或临时方案 + issue 链接。

```java
// 错误码语义、IResponse 契约
// TODO: 待上游修复后移除（#42）
```

## 三禁令

- **复述代码**——不写「做了什么」；命名已自解释处不写；禁止分段装饰（`// ---`、`// ====`）与冗余叙述。
- **裸 TODO / FIXME**——必须关联 issue 链接，否则是欠债而非注释； **既有 `TODO` / `FIXME` 不得顺手删**
  （见上「存量清理」例外：只删确实已解决的）。
- **解释他者**——不解释实现方案 / 调用方逻辑 / 历史问题。 **替别人描述**（注释描述其他类 /
  模块的内部机制或调用流程）必须删——只保留本方法 / 类型的自身契约。

## 两分档（Javadoc）

| 档位 | 适用                                | 要求                                                          |
|------|-------------------------------------|---------------------------------------------------------------|
| 详细 | 公共 API / 工具类（调用方不读实现） | 类级概述 + 契约 + 误用风险；`@param` 等仅在签名表达不了时保留 |
| 极简 | 内部实现（组件内部、工具方法）      | 命名即文档，仅安全 / 协议处加注释                             |

判断标准：类会被其他模块引用、或需解释「何时用 vs 不用 / 有什么坑」，即属详细档。

语言：简约英语为主，中文仅限领域术语。
